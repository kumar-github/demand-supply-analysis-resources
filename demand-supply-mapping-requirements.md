# Demand & Supply Mapping — Requirements Discussion Summary

*A consolidated record of the discussion, decisions made, and open items — not a design or build document. Supersedes the earlier version of this write-up; several points below (band direction, real population size) are corrections, not additions.*

## The Problem, As Defined

HCLTech has 5,000+ employees on bench across all geographies. The goal is to bring that number to zero by matching bench employees to open client/internal demands, so they can be proposed, interviewed by the client, and deployed.

**Phase 1 scope:** MAS capability, bands E1–E3, three personas — **Fullstack Java, Fullstack .NET, and Frontend** (Frontend spans web React/Angular/MERN/MEAN and native mobile iOS/Swift and Android/Kotlin). Everything else in MAS — Testing, Polyglot, DevOps & SRE, Mainframe, TPM, Integration — and everything outside MAS (SAP, Data & AI, ETA, EPS, Oracle, MBAP, etc.) is explicitly out of scope for now.

AAFD (employees whose current project is ending soon, who will become AFD) will extend the same logic later, but the data received so far shows it isn't a simple extension — see "AAFD" below.

Earlier attempts at this (Excel macros, Python scripts doing literal sheet comparisons) failed. The working theory is that literal skill/keyword matching is the wrong approach — this needs something closer to building a "persona" for both sides and comparing those, not comparing raw field values.

## Output Orientation

- **Two teams** will use this: one focused on fulfilling specific demands, one focused on proposing specific supply.
- **Starting point: supply-centric.** For each proposable AFD employee, produce a ranked shortlist of demands to propose them to.
- **Demand-centric view** (for each requisition, ranked candidates) is planned for later, primarily for the AAFD workflow.
- **Parallel proposals are normal.** One employee can be proposed to multiple demands at once; this isn't an exclusive-assignment problem.
- **Review mode: human-in-the-loop.** Generated shortlists are manually reviewed, and corrections are made. The tool is decision-support, not a source of truth that feeds downstream systems directly.

## What The Data Actually Looks Like (corrected)

The first supply file we worked from (297 rows) turned out to be a narrow, pre-filtered slice. The real, unfiltered picture:

| | Supply (unfiltered) | Supply, MAS + E1-E3 + proposable | Supply, Phase 1 (Fullstack Java/.NET + Frontend) | Demand |
|---|---|---|---|---|
| Rows | 1,855, many capabilities (SAP, Data&AI, ETA, Mainframe, MAS, etc.), bands E0–E7 | 836 | **243** | 965 requisitions, ~3,316 open positions (already scoped to MAS Full Stack/Front End — no rescoping needed) |

At 243 proposable people against ~3,316 open positions in scope, this confirms something suspected early on: the hard part isn't finding matches, nearly every proposable person is a plausible candidate for several demands. The value is in producing a good, defensible **ranking**, not in finding candidates at all.

Within Phase 1 (243 rows): 164 Full Stack, 79 Front End. Skill Cluster values split further into personas — "Fullstack Java" (117), "Full Stack .Net" (45), plus web/mobile frontend variants.

The supply and demand skill vocabularies do not line up literally with each other — this is the core problem the matching logic has to solve.

## Matching Logic — Agreed

**Weighting order:** Skill (heaviest) → Band → Location. Both band and location are discounted below an exact match; band's discount is expected to be steeper than location's, though the exact relative sizing is unconfirmed and not yet needed for requirements purposes.

The output must carry the *reasoning* behind a match, not just a percentage — the reviewer needs to be able to defend or dismiss a proposal using it, not just see a score.

### Band — CORRECTED

An earlier version of this document had the band direction backwards. The verified rule, confirmed with a team member:

- Ladder: E1.1 → E1.2 → E2.1 → E2.2 → E3.1 → E3.2 (ignores band/sub-band boundaries when counting steps). E4+ are manager-level and out of scope entirely — this tool doesn't propose managers for technical/client roles.
- Employee band must be **equal to or up to one level above** the demand's required band. Below the demand's band is **not** acceptable — this reverses what was originally stated.
- Two or more levels **above** is a hard exclude.
- Exact-band match ranks above one-level-above, all else equal — the client didn't ask for an overqualified person, and there are real costs to proposing one anyway (margin, retention risk, opportunity cost of using a scarcer higher-banded person here).
- General industry practice, not a hard client rule and not client-specific.
- One open item flagged during this correction: the discount for "one level above" is assumed steeper than the discount for a location flex, but this is the user's own guess, not verified the way the band direction itself was. Treat as unconfirmed.

### Location

- Prime and NV are location *tiers* within India (e.g. Hyderabad/Chennai/Bengaluru = Prime; Vijayawada/Madurai/Nagpur/Lucknow = NV), not a hard constraint layer.
- Flex is **bidirectional**: an NV employee is acceptable for a Prime demand, and a Prime employee is acceptable for an NV demand.
- Net effect: location is close to binary — same city is best, any other India city is still viable.
- **Open/unconfirmed:** whether a demand's "Pan India = Yes" flag means no location constraint at all for that demand (~378 of 965 rows are flagged Yes).
- **Open/unconfirmed hunch:** demand location may sometimes be flexible if the client is open to work-from-home for a strong-skill candidate. Not yet verified — if true, this would mean location needs a third state (hard-required vs. negotiable-if-skill-is-strong), not just same-city/different-city.

### Skill

The hardest piece. Not a literal keyword match — resolved through an **anchor persona** concept:

- A **Skill Cluster** name (supply side) isn't literal — it implies a fixed *core* skill set beyond its literal words (e.g. "Java, Spring Boot" implies SQL too, even though SQL isn't named).
- Skills outside a cluster's core/named skills (Kafka, AWS, Docker, etc.) are **bonus/accessory**, not required — unless the demand explicitly names that specific skill.
- Certain skills are **anchors**: self-sufficient identities that define a persona on their own. Confirmed anchors so far: Java, .NET, DevOps, iOS/Swift, Android/Kotlin, standalone frontend (Angular/React/MERN/MEAN without a backend language present).
- **Anchor precedence:** when a language anchor (Java, .NET, etc.) and DevOps co-occur in the same demand skill list, the language anchor always defines the persona and DevOps is accessory/tooling context (e.g. ".NET Framework, Azure DevOps, C#" = .NET backend using Azure's tooling, not a DevOps role). DevOps only defines the persona itself when **no** language anchor is present at all.
  - A Java/.NET developer can also do DevOps; a DevOps-core person generally does not also do Java/.NET development as a primary skill.
  - This same precedence logic likely needs verifying against the other anchors (iOS, Android, standalone frontend) rather than assumed — not yet done.
- Persona derivation does **not** depend on the hiring manager conversation (not feasible at scale) or on which client/account raised the demand (any client can raise any type of demand). The "Additional Request" free text should be factored in when present.
- **Matching direction on the supply side:** Skill Cluster first (primary, trusted signal — self-reported by the employee), then "Skill Confirmed by Emp," "Passionate Skill," and "Employee Other Skill" as supporting evidence only.
- **Skill Cluster data quality:** treated as trustworthy despite some known mismapped rows (e.g. Skill Cluster reads Full Stack but Skill Cluster Persona reads "Testing" or "Front end"). These are being corrected in a separate ongoing process, not a sign the field is unreliable in principle.
- **Note:** the underlying data already has a `Skill Cluster Persona` field (values like "Fullstack Java," "Full Stack .Net," "Front end," "Testing") that appears to be a pre-computed version of some of this anchor logic. Not yet confirmed how it's generated (formula vs. manual) or how much it can be relied on beyond the known-bad rows above.
- **Not yet built:** the actual anchor/accessory reference table mapping supply's clusters and demand's skill-phrase combinations to shared personas, for the Phase 1 personas (Java, .NET, Frontend/mobile). Agreed to build this together as a living artifact, improved continuously rather than built once.
- Demand data capture is inconsistent across teams — some note "Primary Skill"/"Must have"/"Nice to have," most don't. Standardizing this is future scope, only after a plan exists.

### Anchor/Accessory Skill Table — Approach and Fallback Behavior

- **What it is:** a shared reference table translating both sides' skill vocabulary into a common persona. One row per known supply Skill Cluster or demand skill-phrase combination, recording: the anchor persona it resolves to, its implied core skills (even if unstated in the raw text), and its accessory/bonus skills. Both sides resolve to the same "anchor persona" column, which is what the matcher actually compares — not the raw text.
- **Why a table rather than an alternative:** semantic/embedding similarity was considered and rejected — it would score lexically-similar but semantically-unrelated terms (e.g. "Java, Spring Boot" vs. "JavaScript, Node.js") as close, and can't express precedence rules like "DevOps only defines the persona when no language anchor is present." Running an LLM judgment fresh each time was also considered and rejected — it wouldn't give consistent, inspectable results a reviewer can point to when defending a proposal. A written table is the only option that's stable, inspectable, and correctable.
- **Why two sources, not one normalization step:** supply's Skill Cluster is a closed, curated set (~28 known values) — a lookup problem. Demand's skill field is open free text from many teams with no controlled vocabulary — a parsing/classification problem (detect the anchor within arbitrary word combinations). Both resolve to the same persona label, but the mechanism differs because the raw material differs.
- **Known downsides, accepted going in:** only knows what's in it (new demand phrasings will keep appearing); requires ongoing maintenance, not a one-time build; the core/accessory binary may prove too coarse over time; built from a snapshot of today's skills and will need revisiting as tech trends shift.
- **Fallback behavior (agreed — critical for avoiding false positives):**
  - The table only ever produces a confident persona on an **exact match to a catalogued term**. No fuzzy/partial matching is auto-classified, even when the anchor looks obviously present (e.g. "SpringBoot" vs. "Spring Boot") — that goes to manual review instead of being guessed.
  - **Demand-side unclassified:** excluded from the ranked, candidate-facing shortlist entirely (never scored, never blended in at a discount). Instead logged in a visible coverage queue ("N of the demands this run couldn't be auto-classified") that also serves as the table's growth/build list. This is a routine, expected occurrence given demand's free-text nature.
  - **Supply-side unclassified:** also excluded from shortlists, but treated as more serious — since Skill Cluster is a closed ~28-value set, an unclassified row almost certainly means a source data-quality error (same category as the known Testing/Frontend Skill Cluster Persona mismatches), not a vocabulary gap. Flagged urgently and routed back to whoever owns that employee's record, since it means a real, potentially deployable person is invisible to every shortlist until fixed — a sharper problem than an unclassified demand.

### Anchor/Accessory Skill Table — Build Progress (Java, .NET)

Working top-down by position volume rather than alphabetically. Supply has 28 distinct Skill Cluster values across Phase 1 (243 people); demand has 192 distinct skill-phrase combinations, but the top 40 already cover 92% of open positions (3,042 of 3,316) — the long tail is low-volume and feeds the unclassified/coverage queue rather than blocking progress.

**General rules established while mapping Java and .NET (apply consistently, not just to the rows they came from):**
- A **framework implies its underlying language** even if unstated: "Spring Boot" alone implies Java; ".NET Core"/".NET Framework" alone implies C#. You cannot be a Spring Boot resource without Java.
- A **bare language name implies its typical framework** — e.g. plain "Java" (51 demand positions) is treated as equivalent to "Java Full Stack," and plain "C#, SQL" is treated as implying .NET Framework. **This is a working assumption, not verified the way the band direction was** — reasoning given: demands rarely ask for a raw language with nothing else, so a bare mention is assumed to mean the typical full persona. Flagged as unconfirmed, same treatment as Pan India/WFH.
- **Accessory skills have two tiers, not one:** *unnamed* bonus (never mentioned, doesn't count either way) vs. *named* accessory (explicitly listed, e.g. AWS/DevOps alongside a language anchor) — a named accessory should still nudge ranking upward for candidates who have it, even though lacking it isn't disqualifying.
- **A named skill with nothing else present gets promoted to core, not accessory** — e.g. "Apache Kafka, Spring Boot" (156 positions): Kafka is normally bonus, but since nothing else is named alongside the implied Java/Spring Boot, it's treated as a real requirement here.
- **A named skill paired with an already-complete anchor is a genuine dual requirement, not accessory** — e.g. "Java, Python, Spring Boot" (36 positions): Python is core here, not bonus, since it's an explicit second ask on top of a complete Java persona. (Different reasoning from the Kafka case above, same core outcome — worth keeping the two reasonings distinct.)
- **Dual-anchor exceptions are possible and don't auto-resolve to one side:** "Java, Kotlin" (12 demand positions) is dual persona (Java backend + Android), not a reroute to Android alone, even though Kotlin is normally Android's anchor language.
- **Low-volume anchor-language variants that don't fit the core persona's actual capability are routed to the unclassified fallback, not force-fit or fully modeled:** "C#, WinForms, WPF, WCF" (1 supply person) and "C#, ASP.Net Webforms, WCF" (1 supply person), plus demand's ".NET Framework, C#, WPF" (8 positions) are desktop/legacy-web .NET, not the web full-stack capability "Fullstack .NET" actually means elsewhere. Confirmed this is legacy/maintenance-only work, not new development, so it's parked rather than built into its own persona given the low volume — would be revisited if volume grew.

**Java — resolved:** all Java-anchor supply clusters and the top Java-anchor demand phrases map cleanly to Fullstack Java using the rules above. One reroute caught: "Android, Kotlin, Java" (6 supply people) is Android/mobile persona, not Fullstack Java, despite containing "Java."

**.NET — resolved:** all .NET-anchor supply clusters and top demand phrases map cleanly to Fullstack .NET using the same rules, except the WinForms/WPF/WCF variant noted above (parked).

**Frontend — resolved, with a foundational decision:** React and Angular are treated as **separate sub-personas** within Frontend, not one interchangeable bucket — an Angular specialist is not automatically a good match for a React demand. Full sub-persona set: **React, Angular, MERN, iOS, Android**.

- Supply mapping: React (24 + 9 MERN, since MERN's frontend half is React), Angular (24, incl. a typo variant), iOS (8), Android (6, from "Android, Kotlin, Java" — a reroute away from Fullstack Java despite containing "Java").
- **"HTML, CSS, JavaScript" with no framework named (6 supply people)** — genuinely ambiguous, not a guessable default. Resolved as a third, weaker bucket: **"Frontend — core web, framework unconfirmed,"** matchable against either React or Angular demands but always at a discount versus a confirmed specialist.
- **"Angular,Node.js,React.js" (21 demand positions)** — both frontend frameworks named together. Resolved as **dual-acceptable**: matchable against candidates from either the React or Angular sub-persona (and MERN), rather than forced into one. A deliberate, tagged exception to the sub-persona split, not a default behavior.
- **"Node.js" alone (8 demand positions)** — no UI framework named, only the backend JS runtime. Resolved as a **weak MERN match** (Node.js is MERN's core backend skill), not the ambiguous "framework unconfirmed" bucket — unlike the supply-side case, this one has a specific, named technical anchor to match against, just an incomplete one.
- **Structural finding, not just a data footnote:** standalone Frontend/mobile demand (no Java/.NET/Spring named) totals only ~146 positions across 52 phrases, most at 1–2 positions each — thin compared to 79 Frontend-tagged supply people. Most real React/Angular demand volume lives *inside* Java/.NET full-stack phrases (e.g. "Java,React.js,Spring Boot" — 281 positions) as a named accessory skill on a backend demand, not as a standalone Frontend-persona demand. This means a meaningful share of Frontend-tagged supply may have relatively few pure-Frontend demands to be shortlisted against — a business-relevant finding worth surfacing, not just a modeling detail.

**Not yet worked through:** Testing/Polyglot/DevOps & SRE/Mainframe/TPM/Integration — out of Phase 1 scope entirely, not touched by this table.

**Long tail — resolved.** The 152 demand phrases outside the top 40 (274 of 3,316 positions, 8%) were checked against the anchor rules above rather than left as an assumption:
- **123 phrases (226 positions, 82% of the tail) auto-resolved cleanly** under the existing Java/.NET/React/Angular/iOS/Android rules — just less common phrasings, no new judgment needed.
- **29 phrases (48 positions) had no recognizable anchor.** On inspection, nearly all of these are **scope leakage, not new persona variants** — Selenium, Functional/Manual Testing, Automation Anywhere, IT Service Management, Oracle Agile, Sybase, CA Autosys, C++, Workato, Windchill, Axway APIM, SOA/REST Web Services, Alfresco, and similar read as Testing, Integration, Mainframe, or TPM work sitting inside a demand file that's supposedly pre-scoped to Full Stack/Front End — the same "label doesn't match reality" pattern already found on the supply side (MAS Mapping vs. Capability), now confirmed on demand too. Routed to the unclassified/out-of-scope queue rather than force-fit.
- Two exceptions got small rule additions instead of being dumped into unclassified: **"Next.js" is now a recognized React signal** (it's a React framework), and phrasings naming only CSS/HTML/JavaScript with no framework (e.g. paired with OutSystems) get the same **"Frontend — core web, framework unconfirmed"** treatment already agreed on the supply side.
- **Supply's one remaining unclassified cluster** — "NFT - Performance/Accessibility | JMeter + BlazeMeter + Grafana" (1 person) — is performance/accessibility testing tooling, also out-of-scope-persona rather than a variant of the three Phase 1 personas. Flagged as a Capability/MAS-Mapping mismatch, same treatment as the scope-leakage demand phrases above.

This closes the anchor/accessory table build for Phase 1's three personas (Java, .NET, Frontend) at the level of detail available in the current data snapshot. A structured, standalone reference file (`anchor-accessory-skill-table.xlsx`) now holds the full rule set plus every distinct supply Skill Cluster (28) and demand skill phrase (192), each tagged with a Review Status (Reviewed together / Rule-applied — not individually reviewed / Parked / Unclassified) so it's clear which rows were actually walked through versus resolved by extrapolating the rules.

### Sanity-Check Findings — real employee/demand pairs run through the built model

Before moving to output design, real supply and demand rows were run through the anchor table and full matching model by hand, specifically targeting "Rule-applied" rows the table had extrapolated but never actually been checked against. This surfaced genuine corrections, not just edge cases:

- **Band rule confirmed working as intended:** a same-persona, same-location pair where the employee was one sub-band below the demand was correctly hard-excluded, not discounted — validates the corrected band direction in practice, not just on paper.
- **React/Angular sub-persona split confirmed working:** an Angular-only employee correctly did not match a React-only demand, exactly the false-positive the split was designed to prevent.
- **CORRECTION — Android/iOS/Java demotion, not dropping:** the original rule for "both mobile platforms present" didn't account for a language anchor (Java) also being named, and silently discarded it for the pattern "Android, iOS, Java" (13 demand positions). Fixed: any Phase-1 language anchor (Java, .NET) named alongside an explicit mobile platform (iOS/Android) is demoted to a **named accessory** (e.g. "backend familiarity"), always visible in the reasoning, never silently dropped.
- **CORRECTION — Kotlin does not always mean Android:** Kotlin is a general-purpose JVM language increasingly used for backend work too (Spring Boot has native Kotlin support). The earlier rule assumed Kotlin implies Android strongly enough to justify a dual persona even without the word "Android" present. Corrected: Kotlin only signals Android when "Android" (or another explicit mobile term) is actually named alongside it. "Java, Kotlin" (12 demand positions) now resolves to **Fullstack Java, with Kotlin as a named accessory**, reversing the earlier "dual persona" call for this exact pattern.
- **NEW — Cross-persona discounted matching (identified, not yet built into scoring):** a Java/.NET-persona employee whose Skill Cluster names a Phase-1 frontend/mobile framework (React, Angular, iOS, Android) as an accessory skill should be a **discounted candidate** for a standalone demand in that framework — not a full match (their depth in that framework is unknown from the data), and not invisible either (persona alone shouldn't hide a real, named skill). Ranks **above** the "framework unconfirmed" bucket (at least the specific framework is known) but **below** a true same-persona match. Confirmed **one-directional only** — a Frontend-persona person is not assumed to have hidden backend skill, since if they genuinely had it, self-reporting would likely show it as their primary Skill Cluster instead.
- **OPEN — skill-completeness gradient within a persona (flagged for later, not yet built):** "Java, SQL" and "Java, Spring Boot, REST, Microservices" currently resolve to the identical Fullstack Java persona with no internal distinction, so they'd score identically on skill if band/location/assessment tie — even though the second is a materially richer, more-confirmed profile. Agreed this needs solving eventually; a small number of discrete completeness tiers (not a continuous score) was the leading idea, consistent with how band and location are already modeled. **Important asymmetry to preserve when this is built:** the "bare language implies its typical framework" assumption is reasonable for **demand's** free text (zero signal either way from one bare word) but should **not** be applied the same way to **supply's** curated Skill Cluster — "Java, SQL" is a deliberately distinct, separately-curated cluster value from "Java, Spring Boot," not a shorthand for it. **"Java, SQL" is not the same as "Java, Spring Boot."**

Sanity-checking real pairs (rather than only reasoning in the abstract) is what surfaced all three corrections above — worth treating as a standing practice before trusting any new rule, not a one-time exercise.

### Assessment Score / Rating

- Never a gating factor.
- Among otherwise comparable candidates, a higher score/rating should be preferred and ranked higher.
- ~27% of the proposable pool has no usable score (Yet to Complete or no record at all) — these candidates should not be penalized, simply not boosted.

- **Scope filter:** `Capability == "MAS"` (not the inconsistent "MAS Mapping" field — 278 rows carry a MAS-Mapping label like Full Stack/Front End while actually sitting under a different Capability such as SAP or Data & AI).

## Output Design

Once the matching logic itself was reasonably solid, attention turned to how a shortlist entry is actually presented to a reviewer — since the whole point of carrying detailed reasoning through the matching logic is wasted if the output collapses back down to a single opaque number.

### Current process baseline (for context — what this replaces)

Today, the fulfillment/proposal teams work from a flat, unordered Excel table of matching employees, sent to them as-is. There is no structured reasoning, no persona/band/location breakdown, no tiering, and no logging of who was proposed where — the team **eyeballs the table and proceeds** on judgment alone. Every design decision below (tiered grouping, plain-English reasoning, the proposal log) is a genuine upgrade over this baseline, not a refinement of an existing system — worth keeping visible as the "before" picture when judging how much value the tool adds.

### Reasoning first, not a single fit percentage

The original ask was for fit percentages (100%/75%/50%). Given everything built into the matching logic since — persona/sub-persona, core vs. named-accessory skills, band tier, location tier, assessment as tiebreaker — a single percentage would hide exactly the information needed to defend a proposal. **Decision: the primary output is a small set of labeled reasoning statements, not a percentage.** If a number exists at all, it's a secondary sort key underneath the reasoning, never the headline.

### Card structure — two states, four dimensions

Each shortlist entry (one employee × one demand pairing) is a card with two states:

**Collapsed (default — used when scanning a shortlist):**
- **Overall signal:** a three-tier judgment — **Strong** (same persona, core skills present, band/location exact) / **Good** (persona match but one thing discounted — one-band-above, different city, or a named-accessory gap) / **Weak** (cross-persona discount, or the "framework unconfirmed" bucket).
- **One-line plain-English summary** underneath the signal (e.g. "Right persona; one band above the ask; different city; moderate assessment.").
- **Four dimension rows**, each showing a plain-English judgment, never a raw value at this level:

  | Dimension | Collapsed line shows |
  |---|---|
  | Skill | Persona match strength + what's confirmed/missing in plain words |
  | Band | "Exact" or "One above the ask" |
  | Location | "Same city" or "Different city" |
  | Assessment | The rating word + a plain qualifier (e.g. "Advanced Beginner — Moderate"), **not the raw score** |

**Expanded (on demand, per card):** the same four rows, each now also showing its underlying raw values inline — exact sub-bands, exact cities, the raw assessment score, the full core/named-accessory skill lists. All four dimensions expand together, not one tooltip at a time — this is the view for when a reviewer is about to act on or defend a specific proposal, so all the numbers they might need are in front of them at once, not hidden behind hovers.

**Candidates that fail a hard exclude (band two-or-more below/above, wrong sub-persona, unclassified) never appear on the shortlist at all** — consistent with the fallback behavior already defined for the anchor table. The shortlist only ever shows viable candidates; excluded and unclassified items live in the separate coverage/unclassified log, not mixed into the working view.

### Review interaction model

**Scan-then-drill-down, not a forced one-by-one queue.** The reviewer sees the whole shortlist collapsed, skims it, and expands only the cards they're unsure about, in whatever order suits them — not required to act on each card in sequence before seeing the next. Chosen over a strict queue because the tool is explicitly decision-support (shortlists are "reviewed manually, corrections made," not auto-committed), and a forced sequence would be needless friction over what's meant to be a fast scan.

**Actions available on a card:**
- **Propose** — this pairing is acted on.
- **Reject/Skip** — not now; stays on the list or drops off.
- **Override** — a distinct, deliberate action specifically for the "below policy" tier (one-band-below candidates), kept separate from a normal Propose per the earlier fallback-behavior decision, so it's never mistaken for an ordinary approval.

### Proposal log — built in from day one

**Decision: log every Propose/Reject/Override decision from the first version**, resolving the earlier open item about independent proposal logging. Each entry captures, at minimum:
- The employee + demand pair
- The action taken (Propose / Reject / Override)
- Timestamp and reviewer identity
- **A snapshot of the reasoning as it was shown at decision time** (the skill/band/location/assessment signals) — not just the outcome. This matters because the underlying rules keep evolving (three corrections already made during sanity-checking); without freezing what the tool believed at the moment of the decision, a log entry becomes unexplainable once the rules move on.

**No reviewer-facing interface for this log yet** — it exists purely as backend data for now, not a screen anyone interacts with in the first version. Whether/how a reviewer later sees their own proposal history is left for a future decision.

### Card expand trigger

**Both mechanisms, not one or the other:** per-card click-to-expand for everyday scanning (matches the scan-then-drill-down model), plus a global "expand all" toggle for the audit case — a reviewer about to walk into a client conversation wanting every raw value for every candidate in front of them at once, not clicked open one at a time.

### Skill-completeness gradient — resolved

A separate, discrete tier describing how much is actually confirmed about an employee's own profile — independent of any specific demand, used only as a **tiebreaker among same-persona candidates** (same role as assessment score), never changing the overall Strong/Good/Weak judgment:

| Tier | Meaning | Example (Fullstack Java) |
|---|---|---|
| Core only | Just the implied minimum confirmed, nothing extra named | "Java, SQL" |
| Core + Partial | Core plus one or two named framework extras | "Java, Spring Boot, REST" |
| Core + Rich | Core plus three or more named extras — a fuller, more confirmed stack | "Java, Spring Boot, REST, Microservices" |

**Display:** folded into the existing Skill row's plain-English wording (e.g., "Strong — Fullstack Java, well-rounded profile" vs. "Strong — Fullstack Java, core confirmed, thinner profile") rather than a fifth row on the card — keeps the card from growing just to show this.

### Shortlist-level view (beyond a single card)

- **Grouped by tier, not a flat sorted list:** three visible sections — Strong matches, Good matches, Weak matches — so a reviewer registers how many strong options exist before reading a single card. A flat list with tier badges scattered through it was considered and rejected as harder to scan at a glance.
- **Tiebreaker within a tier: demand urgency/ageing** (`Due Category_New`, `New-Ageing`), since within a Strong tier with band/location/skill all tied, the employee-side signals (which don't vary row-to-row in a supply-centric shortlist) have nothing left to differentiate on. **Confirmed safe to adopt**, not a risky new assumption: the current process is a flat, unordered Excel table the team already scans and acts on by eye with no ordering discipline at all — any sensible default ordering is a strict improvement over that baseline, not a change that could bias behavior worse than today's.
- **Coverage/unclassified log is a separate view, not part of this reviewer's shortlist at all.** Its two flavors (demand-side: routine build queue for whoever maintains the anchor table; supply-side: urgent HR-data-fix flag for whoever owns that employee's record) serve a different job function than "should I propose this person to this demand" — treated as a different audience's view built on the same underlying data, not a tab within this tool's first version.

## Excel Matching Engine — First Build

The Excel deliverable agreed above (`#1 — only the 243`, `#2 — one flat sheet`, `#3 — include Strong, Good and also Weak, and even hard-excluded, greyed out`) has been built and delivered as `phase1-matching-shortlist.xlsx`. This is the first real test of the matching engine itself, not just the anchor table.

**Scoping correction made mid-build — worth recording, not just the numbers:** the originally confirmed scoping ("same broad persona family + the cross-persona-discount case") does not narrow the candidate pool the way it does for Frontend. Frontend has sub-personas (React/Angular/MERN/iOS/Android) to split on; Fullstack Java and Fullstack .NET do not — so "same family" for those two personas is functionally the same as a full cross-join. Concretely: 118 Java employees × 617 Java-persona demand rows ≈ 72,800 possible pairs on their own. The full run produced **89,742 rows** — unreviewable as a flat sheet.

Flagged to the user before generating anything; resolved by adding a **per-employee row cap** on top of the family-scoping rule, confirmed as the preferred fix over the alternatives (urgency-window filtering, or shipping the full cross-join and letting the reviewer filter it in Excel):
- All **Strong** rows kept (rare enough not to need capping — 1,091 total, ~6/employee average, max 21).
- **Good** rows capped at 20 per employee, **Weak** capped at 15 per employee — both ranked by demand urgency (`Due Category_New`, then open position count) before truncating. (Good needed the same cap extended to it once it showed the identical ballooning — up to 205 rows for a single employee before the cap; this wasn't in the original ask but follows the same logic the user approved for Weak.)
- **Excluded** rows capped at the 3 closest near-misses per employee (a band-only miss — otherwise-viable persona/sub-persona but band 2+ off — ranked closer than a wrong-sub-persona miss), rather than every mathematically possible excluded pair. Kept for transparency, not dropped — this was the whole point of showing Excluded rows at all.

Final output: **8,118 rows across 239 employees** (~34 rows/employee average) — reviewable, while still showing every tier including near-miss excludes.

**Classification coverage achieved:**
- Supply: 239 of 243 employees classified into a Phase 1 persona (118 Fullstack Java, 43 Fullstack .NET, 78 Frontend). 4 flagged as data-issue rows at the bottom of the sheet rather than silently dropped — 2 legacy .NET desktop (parked), 1 out-of-scope NFT/performance-testing profile, 1 employee with **no Skill Cluster on file at all** (the most urgent of the four, per the agreed supply-side-unclassified severity — a real, potentially deployable person currently invisible to every shortlist).
- Demand: roughly 97-98% of open positions classified into a Phase 1 persona; the remainder is scope leakage (Testing/Integration/Mainframe/TPM tooling sitting in a file nominally pre-scoped to Full Stack/Front End — the same pattern already found on the supply side), legacy .NET desktop (parked), or genuinely unrecognized phrasings. None force-fit.
- Built as two different mechanisms per the two-sources decision: supply's ~28 Skill Cluster values via an exact-match lookup table; demand's 192 free-text phrases via a token/rule parser implementing the anchor/accessory/persona rules (framework-implies-language, named-vs-unnamed accessory tiers, anchor precedence, all three sanity-check corrections).

**Second correction — Strong/Good/Weak are not simply "show fewer of everything":** the first row-cap pass (all Strong + top 20 Good + top 15 Weak) still produced 8,118 rows, still too much to scan. On review, the fix wasn't a smaller cap — it was recognizing that **Strong and Good are both "propose freely" tiers** (one employee can legitimately be proposed to several demands in parallel — that's normal, not an edge case), so Good should never be hidden just because Strong exists. **Weak, by contrast, is a genuine fallback** ("nothing better, so consider this"), not an additional option alongside Strong/Good. Revised rule:
- All **Strong** rows kept.
- Top **3 Good** rows kept per employee (by demand urgency).
- **Weak** rows shown only for an employee with **zero** Strong and **zero** Good matches (capped at 10 in that case) — never alongside Strong/Good.
- Excluded stays capped at the 3 closest near-misses per employee regardless of the other tiers — a different kind of signal (a band-just-missed case worth an override conversation), not a volume-of-options signal.

Final output: **2,472 rows across 239 employees** (~10 rows/employee average).

**New finding surfaced by this pass: 16 employees have zero Strong and zero Good match anywhere in the current demand book.** Flagged with an amber "⚠ NO STRONG/GOOD MATCH IN SCOPE" banner in the sheet rather than silently having a short or empty block. Nearly all are Frontend/mobile specialists (iOS, Angular, "framework unconfirmed") — consistent with the earlier structural finding that standalone Frontend/mobile demand is thin relative to Frontend-tagged supply. A few of these have no Weak fallback either (only near-miss Excluded rows, e.g. band one level below the only demands that exist for their specific skillset) — genuinely nothing to propose them to right now under the current rules, not a modeling gap.

**Employee Band and Employee Location were missing as their own columns** in the first pass (shown only in the employee's banner text) — a real usability bug, not intentional; fixed so every row carries them and the sheet is properly sortable/filterable on those fields.

**Display vs. engine — a distinction worth keeping straight going forward:** two different reductions are at play, and only one of them is a display choice.
- **Candidate scoping** (same persona family + the cross-persona-discount case) decides which employee×demand pairs get scored *at all*. This is a matching-engine-level decision — some version of it has to exist regardless of output format, though a web app computing a demand's candidates on the fly (rather than pre-computing a full export) could make it less rigid than it is here.
- **The per-employee tier caps** (top 3 Good, Weak-only-as-fallback, top 3 Excluded) are purely an export limitation on top of an already-fully-scored set. The engine classifies every pair in the scoped candidate set regardless; the cap only decides how many of those already-computed rows get printed into a given flat file. None of it changes any pair's Strong/Good/Weak/Excluded classification.

**Decision (not yet built — no Excel rebuild done):** since the Excluded cap is purely a display choice and a flat Excel sheet is a poor format for "maybe useful, maybe not" rows, **Excluded will be dropped from the Excel output entirely** next time it's rebuilt. In a web app, this reverses — Excluded becomes something the reviewer opts into seeing (a filter/toggle), rather than something pre-baked into a fixed export at a fixed cap. The **16 no-match employees stay visible** regardless — that's a finding, not an artifact of which tiers are shown, and pulling those into their own list (for whoever can act on the underlying skill/demand gap) was confirmed as worth doing, once we're ready to build again.

**Full methodology, tier definitions, and the open/unconfirmed items list are documented in the workbook's own "Read Me" tab**, not duplicated here — that tab travels with the file so a reviewer opening it later has the reasoning in hand without this write-up.

**Not yet done:** the proposal log (backend logging of Propose/Reject/Override) has no home yet since there's no interface to act from — this Excel is read-only output, not a place decisions get recorded back into the tool. That remains for the web app.

## Web App — Architecture & Technology (Phase 2 kickoff, decided 2026-09-27)

**Context that shaped these choices:** the web app will be built by a small dev team (not solo), on a Java/Spring Boot-leaning team (the same profile as the wider org), reading and writing the already-built-and-tested Postgres schema (`full_db_design.sql`), reimplementing `engine.py`/`build_matches.py`/`classify_inputs.py`'s logic per the build → parallel-run → sunset plan above.

**Backend: Spring Boot (Java), layered.**
- `controller` (REST) → `service` → `repository` (Spring Data JPA) against the existing Postgres schema.
- **Matching engine, ported not wrapped** — `ClassificationService` (supply + demand classification) and `MatchingService` (skill/band/location signal + `overall_tier`) are faithful Java re-implementations of the Python logic, reading rules from `skill_cluster_rules`/`skill_tokens`/`accessory_weights` (the live source of truth, per the earlier architecture decision) rather than calling into Python at runtime. This is the single riskiest, highest-effort piece of the whole build — scope and staff it as its own workstream, not a side effect of building CRUD screens. The already-agreed parallel-run testing plan is the safety net for this port specifically.
- **Ingestion** — `RefreshService` using Apache POI to parse the AFD-Supply/Demand Excel, applying the hash-diff/upsert/soft-delete logic already documented in the SQL file's refresh-safety section. Manually triggered for v1 (upload or point-at-path), matching how the Python tool is run today; scheduling can be added later if needed.
- **Schema migrations** — Flyway, versioned from `full_db_design.sql` as migration V1. The schema has already been through 15+ revisions during Phase 1 review; treating every future change as a tracked migration (not a hand-run `ALTER`) continues that discipline.

**Frontend: Vaadin Flow, not React** — reconsidered after direct discussion (2026-09-27). Chosen over a React SPA because: it keeps everything in one Java codebase (no separate frontend build/deploy, no TypeScript, no CORS), it matches the actual team's skillset (Java/Spring Boot-leaning, same org that trains Java developers), and the UI itself — a card-based internal reviewer tool for a couple of teams, not a public consumer app — is exactly Vaadin's target shape. Real trade-offs accepted knowingly, not overlooked:
- **Licensing**: Vaadin Flow core (layouts, buttons, basic Grid, Dialog) is Apache 2.0/free; Charts, Board, CRUD, and some advanced Grid features require a paid Vaadin Pro/Prime subscription. What's scoped so far (cards, expand/collapse, filtering, basic lists) looks like it stays free — confirm per-component before committing, not mid-build.
- **Server-side UI session state** — more memory per concurrent open browser tab than a stateless API + client-rendered SPA. At this app's scale (an internal tool for a couple of review teams) this is inside Vaadin's normal operating range, not a real risk.

**A REST API layer is also being built, alongside Vaadin, not instead of it.** Vaadin views call the shared service layer directly (in-process — no reason to route the UI through its own REST API and add latency for nothing); REST controllers under `/api/**` call that same service layer for any consumer outside the browser (a future mobile app, a reporting tool, another team's integration). One Spring Boot deployable serving both presentation layers for v1, unless a real scaling reason to split them shows up later. This was an explicit decision, not a default — nothing in current scope requires the REST layer today, but it was chosen deliberately as forward cover rather than left out and bolted on awkwardly later.

**Still open — genuinely unknown, not guessed at:**
- **Auth** — the `users` table already models a reviewer/admin role, but whether it's backed by HCLTech SSO/LDAP or a simpler login mechanism is infra-dependent information this discussion doesn't have.
- **Deployment target** — on-prem, HCLTech cloud, containers — same reason, not assumed here.
- **Parallel-run comparison harness** — the build → parallel-run → sunset plan needs an actual tool (script or test suite) that runs the same Excel input through both the Python pipeline and the new Java pipeline and diffs `match_candidates` output row-for-row. This should be scoped as an explicit early deliverable of the web app build, not something improvised once the port is "basically done."

## CLI Package — Bug Fixes and Design Decisions (Tasks #1–#15)

The Excel deliverable above was later wrapped into a standalone local tool (`bench-match-cli`) so a fresh shortlist can be regenerated from new AFD-Supply/Demand exports without a chat session. Building and terminology review of that tool surfaced eight fixes/decisions, all implemented in both `engine.py`/`build_matches.py` and the thin one-row-per-employee companion view:

1. **Cross-persona matching removed.** A Java/.NET employee's named frontend accessory was never used to propose them against a standalone Frontend demand — contributing zero rows to real output, so the code path was deleted rather than kept dormant.
2. **REST/RESTful API is no longer a tracked named accessory**, on either side. Spring/Spring Boot already implies it; tracking it separately was double-counting the same signal.
3. **MAS Mapping check added** — a reviewer-facing, validation-only flag when a demand's MAS Mapping value disagrees with the persona the engine actually derives from its skill text. Never used to filter or match; the safety net for whenever the source export stops being pre-filtered to Full Stack/Front End the way it is today.
4. **Additional Request is surfaced, never parsed.** Carried through verbatim to both output workbooks for manual reviewer attention; the engine never reads or scores it.
5. **MEAN (Mongo/Express/Angular/Node) is now its own sub-persona**, mirroring MERN. Before this fix, a MEAN-shaped demand's Node+Mongo+Express signal was matched before Angular was ever checked, so it was silently mislabeled as needing React — which would have wrongly excluded a real Angular candidate. No real MEAN row exists in the data yet; the fix is in place for whenever one shows up.
6. **Spring Boot / Web API-MVC-Entity Framework must actually be confirmed, not assumed from the base language alone.** This was a real, live bug: an employee listed as just `"Java, SQL"` and a demand asking for `"Java, Spring Boot"` classified identically (same persona, no accessory difference), so the engine scored a framework-absent employee as a full Strong match — affecting 23 real supply rows against 225 demand rows naming Spring Boot explicitly. **Explicit decision on how to treat it:** this is not actually a match at any strength — but rather than exclude it outright, it's deliberately capped at **Weak**, the same treatment already given to Frontend's existing "framework unconfirmed" bucket, purely for consistency across the two cases. This is acknowledged as *not* the "correct" answer, a stopgap until a proper skill-weighting mechanism exists (see Parked Items) — at which point this and Frontend's framework-unconfirmed bucket should both be revisited together.
7. **Supply-side and demand-side named accessories now share one canonical vocabulary.** They had drifted into two different string sets for the same skills — supply was hand-typed (`"Cloud (AWS/Azure/GCP)"`), demand was auto-generated from a separate token list (`"Amazon Web Services (Aws)"`, `"Azure"`, `"Gcp"`) — so a real cloud-experienced employee could show a false "named accessory gap" against a demand asking for AWS/Azure/GCP specifically (the same shape of bug as REST/RESTful API above). Fixed with a single canonical registry (`ACCESSORY_CANONICAL` in `engine.py`) that both sides resolve through before comparison.
8. **Skill gaps are now weighted (Critical/Important/Minor), replacing the flat one-discount-for-any-gap rule.** Before this fix, ANY named-accessory gap capped a match at Good identically, regardless of whether the missing thing was load-bearing or a nice-to-have — Spring Boot and Redis were treated the same once a gap fired. Agreed weighting (v1, explicitly correctable): **Framework** (the persona's real framework — Spring Boot / Web API-MVC-Entity Framework / React or Angular itself) = **Critical**, capped at Weak; **Microservices, Cloud, DevOps, Kafka** = **Important**, capped at Good; **Docker, Hibernate, Web Services, Redis, GraphQL, Python** = **Minor**, informational only — no longer caps the tier, so an employee missing only a Minor accessory (e.g. Hibernate) can now correctly reach Strong. This also **folds Task #6's framework-confirmation check and Frontend's pre-existing framework-unconfirmed bucket into the same severity concept** (both are the "Framework" = Critical case), one mechanism instead of two, per the explicit decision at the time Task #6 was built. Verified against real data: 88 real employee-demand pairs that were previously flat-capped at Good (Minor-severity gaps only, e.g. missing Hibernate/Python/Docker, otherwise a clean band/location match) now correctly surface as Strong.

9. **Architecture/gap review, three fixes.** Requested as a direct "is there anything to improve" review of the engine and architecture, not tied to a specific bug report — found and fixed three real issues:
   - **MEAN was incompletely wired into `build_matches.py`.** Task #5 added the MEAN sub-persona and updated `FRONTEND_EQUIV`, but three separate hardcoded sub-persona lists in the Frontend matching branch (a demand that accepts either React or Angular; a framework-unconfirmed cross-match; a weak Node.js-only demand) were never updated to include it — a real MEAN candidate would have hard-excluded against exactly the demands MEAN's Angular half should qualify for. This didn't show up in testing because no real MEAN row exists in the data yet; fixed for whenever one does, and verified with synthetic MEAN rows against all three demand shapes.
   - **Dead constants removed from `engine.py`** (`JAVA_TOKENS`, `DOTNET_TOKENS`, `DEVOPS_TOKENS`, `IOS_TOKENS`, `ANDROID_TOKENS`, `RAW_SQL_TOKENS`) — none were ever read by the actual classification logic, which hardcodes the same literal strings directly. `ANDROID_TOKENS` was worse than merely unused: it bundled in `'kotlin'`, directly contradicting the deliberate "Kotlin does not imply Android without an explicit mobile term" fix documented a few lines below it in the same file. This is exactly the kind of double-source-of-truth drift that produced three of the real bugs already found this project (REST, MEAN-as-React, Cloud/AWS naming) — removed as a landmine rather than left in place.
   - **"Kotlin" given an explicit Minor weight** instead of silently falling through to the Important default — no supply-side entry can currently confirm it for a Java employee, so a demand naming Kotlin will always show a gap; making the weight explicit keeps that visible rather than hidden behind a default.

10. **Messaging/Kafka/JMS/RabbitMQ handling — correction to how Task #8's parked "Messaging" finding was originally framed, plus one real bug fixed.** The earlier write-up (Parked Item #16, below) described "Messaging" as the same shape of gap as Task #7's Cloud/AWS/Azure/GCP fix. That framing was wrong and has been corrected: Cloud/AWS/Azure/GCP really are different strings for the *same* thing at the granularity this project uses, so unifying them was fixing a bug. Messaging vs. Kafka/JMS/RabbitMQ are different strings for genuinely *different* things — Messaging is an architecture-level term, Kafka/JMS/RabbitMQ are specific technologies underneath it — so they were never supposed to unify, and it's correct that "Messaging" doesn't match a specific technology token. Decision: **kept deliberately separate.** "Messaging" stays its own canonical accessory with no demand-side tokens registered (a supply-side-only label until/unless a demand row is ever phrased generically as "Messaging" itself, which none currently are). While checking this, found a real, live bug: **JMS was completely untracked** — a real demand row ("JMS, Java, React.js") was silently invisible to the engine, not recognized as any named accessory at all. Fixed by adding **JMS** as its own canonical accessory (Important, same tier as Kafka). **RabbitMQ** added alongside it for the same reason, proactively — zero current demand rows mention it, but it's the same kind of gap waiting to happen and costs nothing to close now. Verified against real data: fixing JMS alone moves exactly 1 pairing row from Good to Strong (Strong 1213, up from the corrected Task #9 baseline of 1214 — see the note below on that baseline correction), isolated and confirmed via direct A/B comparison of the two states.

    **Also implemented this task, DB-only (no engine behavior change):**
    - **Canonical accessory vocabulary represented as a real DB column**, not just a Python dict: `skill_tokens.canonical_accessory` in `full_db_design.sql` now mirrors `engine.py`'s `ACCESSORY_CANONICAL`/token-to-canonical mapping (e.g. the `aws`/`azure`/`gcp` tokens all carry `canonical_accessory = 'Cloud'`). Resolves Parked Item #15's first half.
    - **Persona dimension added to `accessory_weights`** — a new nullable `persona_id` column (NULL = generic default applying to all personas), with the primary key changed to a dedicated `weight_id` and uniqueness on `(accessory_name, persona_id)`. This is infrastructure only: no override values exist yet, `engine.py`'s `ACCESSORY_WEIGHT_OVERRIDES` dict is currently empty, and every real weight today still resolves through the generic persona-agnostic table. The mechanism exists for the day a persona-specific override is actually needed (e.g. if Cloud experience should weigh differently for Frontend vs. Java) without a further schema change.

That number was never re-checked after the Kotlin weight fix landed, and was wrong — the real, reproducible Task #9 baseline is **Strong 1214**. Root cause: 9 real demand rows mention Kotlin, and giving it an explicit Minor weight (rather than the implicit Important default) had a real, correct promotion effect through the same "flat cap removed" mechanism as Task #8's Hibernate/Python/Docker promotions — this was simply never re-verified and re-reported at the time. 11. **Supply-side Sub Band values outside the E1.1–E3.2 ladder (E0.x, E2.3, or anything else) are now a visible, flagged data-quality issue — resolves Parked Item #9.** Before this fix, the two known cases (E0 and E2.3) failed differently and both badly: a Band=E0 row was filtered out before classification ever ran, so it never appeared anywhere — no trace, not even a count; a Band=E1/E2/E3 row with an invalid Sub Band (E2.3) *did* get a normal persona from its skill-cluster text, and its bad band only showed up later, at scoring time, as an "unresolved, needs manual check" match — present, but easy to miss and not marked as bad data. Fixed by treating any Sub Band outside the six defined ladder values as a data-quality override at classification time: persona is cleared and the row is routed into the same red-highlighted "DATA ISSUE" block the workbook already uses for unclassifiable skill-cluster rows, so a reviewer sees one consistent place for "this employee needs a band correction before they can be matched," regardless of which way the row was previously going wrong. Verified with a synthetic E2.3/E0.2 test — both correctly flag with the expected message. Against the real 243-row Phase 1 population today, this fix is currently dormant (0 rows trigger it) — see the finding directly below for why, on the E0 side specifically.

    **A related finding surfaced while implementing this — RESOLVED.** Widening the Band-level filter to admit E0 doesn't actually make the real E0 rows visible: of the 22 real Band=E0 rows in the source file, 21 (all Sub Band E0.2, MAS Mapping = "Full Stack") have `Capability` = blank/NaN, not `"MAS"` — they fail the *Capability* filter, which sits earlier in the pipeline than the Sub Band check above. **Decision: blank Capability is ignored — these rows stay out of scope, as the Capability filter already treats them.** No code change needed; current strict `Capability == "MAS"` behavior is correct as-is. This also means the E0-side of this fix is, for now, permanently dormant against real data (nothing with Capability=MAS currently has Band=E0) — it exists for whenever a genuine MAS-capability E0 row with a bad Sub Band shows up, and the E2.3-shaped case (a real MAS row with an invalid, non-blank Sub Band) is the one it's actually guarding against day to day.

12. **Checked whether `Capability`/`Sub-Capability` are more reliable fields than `MAS Mapping` for identifying persona — they are not, by a wide margin.** Direct data comparison against the real 259-row Full Stack/Front End population: using the engine's own skill-cluster-text-derived persona as ground truth, `MAS Mapping` agrees with it in 252/259 rows (97%); `Sub-Capability` agrees in only 218/259 rows (84%). Where the two fields disagree with each other, `MAS Mapping` is the one that matches the engine's derived persona in 35 of those 36 cases — `Sub-Capability` is right only once. **`Capability == "MAS"` was already the primary Phase 1 scoping filter** (in place since Task #1, documented in `classify_inputs.py`'s own module docstring) — that part of the instinct was already correct and already implemented, nothing to add there. `Sub-Capability`, however, tested as the *less* reliable of the two checked fields for the specific question of Full Stack vs. Front End persona — it should not replace or supplement `MAS Mapping`'s existing role as the check-only validation column. `MAS Mapping` remains the right field for that purpose.

    **`Sub-Capability`'s actual values**, within `Capability == "MAS"` (920 rows — already our scope filter), for reference: Full Stack (228), Polyglot (227), Testing (213), Front End (89), DevOps & SRE (48), Mainframe (46), Tech Project Management (44), Integration (23), Architect & Emerging (1), Others (1) — 10 distinct values. Only "Full Stack" and "Front End" line up with the two Phase 1 personas in scope; the rest sit outside Phase 1 entirely, the same boundary `MAS Mapping`'s own non-Full-Stack/Front-End values already draw.

13. **Sub-Capability implemented as a check-only reviewer flag, per the finding above — never a scoping filter.** Tested the filter version first, directly against real data: requiring `Sub-Capability` to agree with the engine-derived persona would have dropped 19 rows from the pre-band/status-filtered Full Stack/Front End population, and of those, the engine's own skill-text classification sided with `MAS Mapping` (not `Sub-Capability`) in 17 of 19 cases — 12 of them tagged `Sub-Capability = "Polyglot"` while actually listing skills like `"Java, Spring Boot, REST"` or `"HTML, CSS, Javascript"`. Using it as a filter would have silently removed real, deployable candidates. Implemented instead as a flag, exactly mirroring `MAS Mapping`'s own existing check (`mas_mapping_check` in `classify_inputs.py`): a new `sub_capability_check()` function compares `Sub-Capability` against the engine-derived persona and, on disagreement, sets a note — never excludes, never changes scoring. Surfaced on the **employee header line** in the main workbook (⚠ Sub-Capability check: ...) rather than as a per-row column, since it's a property of the employee, not of a specific demand pairing — and added as its own column in the thin one-row-per-employee view, where it fits naturally. Verified against real data: 36 of the 239 classified Phase 1 employees are flagged (a broader net than the earlier 19, since this check also catches cases where Sub-Capability names a value that IS Full Stack/Front End but the wrong one for the derived persona, not just cases where it names something else entirely). Confirmed no change to matching output — Strong/Good/Weak/Excluded counts (1213/647/16/717) are identical before and after, as expected for a check-only addition.

14. **Demand-side Sub Band values outside the E1.1-E3.2 ladder — Task #11's supply-side fix, extended to the demand side, resolves Parked Item #17.** This was worse than the supply-side version, not just an unlabeled duplicate: a demand row with an invalid Sub Band (real examples: `T0`, `E4+`/`E5.x`/`E6.x`) stayed in the matching pool and scored `quality='unresolved'` against every employee paired with it — `overall_tier()` treats that as one ordinary discount, the same bucket as "one band above" or "a different city." So a demand whose real band position isn't even known could still surface as a **Good or Weak proposal** with no visible warning beyond buried detail text — actively misleading, not just ambiguous. Fixed the same way as Task #11: these rows are now excluded from the matching pool entirely (persona cleared, same treatment as any other unclassifiable demand row) and counted out separately in the classification summary and the workbook's "Demand classification coverage" note, so they're distinguishable from ordinary scope leakage. A full per-row visible flag (mirroring supply's red-highlighted DATA ISSUE block) is a separate, not-yet-built view for demand-side issues generally — noted in the main write-up as "Coverage/unclassified log," explicitly out of this tool's first version — so this fix stops at removing the misleading match and improving the aggregate count breakdown, not building that view. Verified against real data: 26 real demand rows have an invalid Sub Band; removing them from the pool changes the total pairing count by exactly 2 rows (Good 647→646, Weak 16→15, Strong and Excluded unchanged) — small and exactly the expected shape, since most of the 26 rows either generated no candidate rows at all or were already excluded for other reasons (persona/skill-cluster) before this fix.

15. **React/Angular now tracked as a named accessory when they co-occur with Java/.NET — resolves Parked Item #6 (anchor precedence beyond DevOps), the standalone-frontend-vs-language half of it.** Checking this item found two separate things: mobile anchor precedence (iOS/Android vs. Java/.NET) was **already correctly implemented** — mobile wins and the language gets demoted to a *kept* named accessory (e.g. `"Java (backend familiarity)"`), verified against 3 real demand rows. But standalone-frontend precedence (React/Angular vs. Java/.NET) had a real inconsistency: Java/.NET correctly wins the persona (as intended — a Fullstack dev's frontend mention doesn't make them a Frontend persona), but unlike the mobile case, the loser was **silently dropped entirely** rather than kept as a named accessory — e.g. `"Java, Spring Boot, REST, React"` recorded no accessory at all, even though Cloud/DevOps/Docker/Python/Hibernate and everything else on the accessory list *were* tracked normally when named alongside Java/.NET. Confirmed with the user this should be tracked the same as those. Implemented: React and Angular added to `ACCESSORY_CANONICAL`/`ACCESSORY_WEIGHT` (both **Minor** — same bucket as Docker/Hibernate/Python, informational only, doesn't cap the tier — not Important like Cloud/DevOps, since it's a nice-to-have for a backend persona, not framework-defining), with both `engine.py`'s demand-side parser and the six affected `SUPPLY_TABLE` entries updated (and their `completeness` tier bumped accordingly, e.g. `"Java, Spring Boot, REST, React"` moves from Core only to Core + Partial). Where React/Angular instead *define* the persona (a standalone Frontend demand or employee), they're deliberately excluded from the named-accessory list — a persona isn't its own accessory. Verified against real data: Strong/Good/Weak/Excluded counts unchanged (1213/646/15/717 — expected, since Minor severity is informational only by design), but the skill is now visibly called out in the reasoning/summary columns for 1,279 real pairing rows that mention React or Angular, where it was previously invisible entirely. **The Minor-severity call was flagged to the user as my own judgment, not an explicit instruction — user has since confirmed it as correct (2026-09-27). No longer an open question.**

## Database Design Review (2026-09-27) — pre-Phase-2, before anything is built on top of it

With every Parked Item now either resolved or explicitly Phase 2, this was a direct check on the design itself before Phase 2 work starts depending on it: does it actually work, do we need every table, what can be improved.

**Headline finding: the schema had never been created, loaded, or queried against a real database — only verified by inspection against `engine.py`, task by task.** Fixed as part of this review: spun up a real Postgres 16 instance, ran the full schema against it end-to-end (all 14 tables, all indexes, no errors), then wrote real test rows to exercise every fix below rather than trust them by reading — see verification notes per item. Recommend doing the same (schema + a real load of the actual Excel data) as an early Phase 2 step, before the web app is built assuming this design is sound.

**Table count: one dropped, three flagged as not-yet-live.**
- `demand_source_snapshots` (point-in-time "what did this demand say last Tuesday") — already marked optional/speculative in the original design, and nothing in current scope actually needs it. Removed entirely rather than carried unused; trivial to add back if a real need shows up.
- `skill_cluster_rules`, `skill_tokens`, `accessory_weights` — these mirror `engine.py`'s Python dicts (`SUPPLY_TABLE`, the token vocabularies, `ACCESSORY_WEIGHT`), but **nothing today makes the engine actually read from them.** Until the engine is refactored to load its rules from these tables, they're a second, hand-maintained copy of the same logic that will drift from `engine.py` over time — the same shape of bug as the Task #9 Kotlin-weight reporting slip earlier in this project, just live-in-two-systems instead of live-in-one-and-stale-in-a-doc. Flagged directly in the schema comments now; not resolved by this pass — needs an explicit Phase 2 decision (wire the engine to read from them and make them real, or keep them documentation-only and say so).

**Four fixes applied to the schema, each verified against real Postgres, not just read:**
1. **`supply_enriched` had no soft-delete pattern; `demand_enriched` did.** `supply_overrides`, `demand_candidate_decisions`, and `match_candidates` all FK to `employee_id`, and the design said supply is "fully truncated/upserted" every refresh — a real risk of orphaning review history or match rows when an employee drops off the AFD-Supply export (staffed, left bench). Added `is_active`/`inactive_since` to `supply_enriched`, mirroring demand's existing pattern. Verified: flipped `is_active = FALSE` on a test row with a `supply_overrides` row referencing it — the override survived untouched, as intended.
2. **`accessory_weights UNIQUE (accessory_name, persona_id)` didn't protect what it was meant to** — standard SQL treats `NULL <> NULL` for uniqueness, so multiple generic-default (`persona_id IS NULL`) rows for the same accessory could be inserted without violating it. Added a partial unique index (`WHERE persona_id IS NULL`) to close the gap. Verified: a second `('Cloud', NULL)` insert now correctly fails with a unique-violation error.
3. **`match_candidates.run_id` was nullable**, weakening its own `UNIQUE (employee_id, demand_id, run_id)` constraint the same way. Changed to `NOT NULL` — every row is produced by a run.
4. **Free-text status/signal columns had no `CHECK` constraint** despite small, fixed value sets — cheap insurance against a typo silently breaking a UI filter later. Added `CHECK` constraints to `classification_status` (both sides), `match_candidates.skill_signal`/`band_signal`/`location_signal`, `demand_review_state.status`, `demand_candidate_decisions.status`/`engine_tier_at_decision`, `refresh_runs.source`/`status`. Also made `decision_history.changed_by` `NOT NULL` — a nullable actor undercut the one table that exists specifically to answer "who did this." **The `skill_signal`/`band_signal`/`location_signal` value lists were pulled directly from `build_matches.py`'s `skill_signal()`/`band_signal()`/`location_signal()` functions while implementing this**, not guessed from the schema's own (incomplete) comments — the first draft of this fix would have wrongly rejected real values like `'weak_node'`, `'too_senior'`, and `'same_city'`/`'diff_city'` (the schema comment only listed a partial set, and had the location values wrong entirely). Verified: inserted a real `match_candidates` row using actual engine-produced values (`skill_signal='weak_node'`, `band_signal='unresolved'`, `location_signal='diff_city'`) — accepted; a deliberately bogus `classification_status` value was rejected as expected.

Updated file: `full_db_design.sql` (revision note at the top dated 2026-09-27 has the full detail).

### `RefreshService` — Excel → DB ingestion (2026-09-28)

Ported `classify_inputs.py`'s filtering/classification/hashing logic to Java (`RefreshLogic`, no Spring/JPA dependency, independently verifiable), an Apache POI sheet reader (`ExcelSheetReader`), a get-or-create `Persona`/`SubPersona` lookup (`PersonaCatalog`, since neither table is pre-seeded), and the `RefreshService`/`RefreshController` that wire it all to the repositories inside a transaction, implementing the hash-diff/upsert/soft-delete algorithm already documented in `full_db_design.sql`. Two schema gaps found and fixed along the way, both additive Flyway migrations:
- **`supply_enriched` was missing `sub_band`** (only had the coarse `band`) — would have silently broken band-ladder scoring the moment matching read from the DB instead of a CSV. Fixed via `V2`, which also added `bench_ageing_days` and corrected a stale schema comment about what `source_row_hash` actually covers.
- **`rating`/`score`/`balance_positions`/`due_category`** — needed by the assessment-signal and per-employee capping logic (see `MatchingRunService` below), had no columns at all yet. Fixed via `V3`.

Three known, deliberate gaps left in `RefreshService` (documented in its own class Javadoc): `needs_reattention` is never set (needs `demand_review_state`, which has no JPA entity yet — that whole reviewer-workflow slice remains explicitly out of scope); the human-readable `sub_capability_note`/`mas_mapping_note` reason text isn't persisted, only the boolean flags (fully re-derivable on demand from the stored raw value + persona, so nothing is actually lost); `cluster_name_raw` is populated from the raw Excel column literally named `"cluster"`, a best-effort mapping worth confirming against one real demand row.

**Real bug found and fixed during verification (2026-09-29):** a real employee's `Rating` cell contains the literal text `"NA"`; pandas (which `classify_inputs.py` runs through) silently treats that as missing, but the Java POI reader read it as the literal string. Fixed by teaching the Java `nz()` helper the same null-token vocabulary pandas uses by default, so a raw field containing `NA`/`N/A`/`NULL`/`NaN`/`None`/etc. is treated as null the same way on both sides — this only affects stored/normalized output, not classification itself. **Verified PASS on a real machine (2026-09-29) after the fix**, checking all 243 supply and 972 demand rows (including the new `sub_band`/`bench_ageing_days`/`rating`/`score`/`balance_positions`/`due_category` columns) against real Python-produced ground truth.

### `match_candidates` gets a real producer — `MatchingRunService` (2026-09-29)

Before this, nothing in the codebase actually ran the matching engine across every supply × demand pair and wrote rows — `MatchingService` was only ever called from standalone verification harnesses. Closed in four steps, full parity with `build_matches.py`'s real per-employee ranking/capping behavior (not a scoped-down stand-in):
1. **Schema** — the `rating`/`score`/`balance_positions`/`due_category` columns above.
2. **Ported the ranking/capping logic** — `assessmentSignal()` (rating/score → collapsed/expanded text, with the "not yet assessed" bucket for the ~27% of the pool with no usable score, per the earlier agreement), `ageingRank()` (urgency ranking from `Due Category_New`), and `capEmployeeRows()` (the exact tier-cap rule from the Excel Matching Engine section above: all Strong kept, top-3 Good by urgency, Weak only as a zero-Strong-zero-Good fallback capped at 10, top-3 Excluded near-misses) — all added to `MatchingService.java`.
3. **`MatchingRunService`** (`POST /api/matching/run`, no request body — always runs against whatever data is currently active) — iterates active, classified supply × same-persona-family candidate demand, computes all four signals, applies the cap, and fully truncates/rewrites `match_candidates` each run (the table is documented as re-derivable, not additive). Two more real gaps found and fixed ahead of this: `supply_enriched.completeness` (display-only) and, more importantly, **`demand_enriched.classification_note`** — `DemandClassifier` already computed the weak-MERN/etc. status text correctly but it was never persisted, and `skillSignal()`'s Frontend branch needs that exact text to detect the weak-MERN case; without it, a weak-MERN demand would have been wrongly scored as a full match and would have wrongly hard-excluded a real MEAN candidate. Both added via `V4`.
4. **End-to-end verification** against a real `build_matches.py` run on the same data — confirmed exact **twice**: once in-sandbox against a stale snapshot (2,591/2,591), then **on a real machine against a fresh regeneration straight from the user's own current Excel files: 2,586/2,586 rows, 0 extra rows, 0 field mismatches** (tier, all three signal qualities, assessment rank, ageing rank, and the full one-line reasoning string all checked per row) — and confirmed to match the row count the live app's own `/api/matching/run` produced against the real database. Two independent implementations, Python and Java, agree exactly, row for row, field for field.

This closes the parallel-run verification gap flagged in the architecture section above — the matching engine, not just classification, is now proven to match Python exactly on real data, in the actual database-writing code path, not just in a standalone harness.

### A real classification bug, found from the Excel output itself (2026-09-29/30)

Reported directly from a generated shortlist: a demand naming "Angular,Java,React.js" matched 100% (Strong) against a plain Java/SQL employee, independently flagged by the MAS Mapping check as disagreeing. Root cause: the Java/.NET anchor-precedence branch fires unconditionally whenever "Java"/".NET" is present, even when a frontend framework is also named and no backend framework confirms it — unlike the mobile-anchor branch right above it, which already correctly demotes Java/.NET when iOS/Android is present. Affects 312 of 899 demand rows, 32 distinct skill-cluster patterns — not a rare edge case.

**First fix attempt was tried and rejected**, worth recording since it's a real dead end, not just a footnote: gating persona routing itself on framework confirmation reclassified ~180 legitimately Fullstack Java/.NET demands to Frontend — including one whose own Additional Request text literally said "no GUI experience needed," and one skill-cluster phrase ("Devops,Java Full Stack,React.js") tagged Front End on one real job requisition and Full Stack on another, by different people. This is proof the ambiguity genuinely lives in the source data and isn't resolvable by any token rule in either direction — not a case where more clever parsing would have found the "right" answer.

**Fix landed:** anchor routing reverted to unconditional — persona assignment never silently changes, same as before this was found. Instead, a new standalone reviewer-only flag — "Frontend Anchor check" — mirrors the existing MAS Mapping check pattern exactly: checked against the engine-derived persona, surfaced for reviewer judgment, never used to route or score. Added on both sides (`classify_inputs.py`'s `frontend_anchor_check()`; Java's `RefreshLogic.frontendAnchorCheck()`/`frontendAnchorNote()`), persisted via `V5`, and wired into both output workbooks' columns. A verification assertion was added specifically so a future change to this logic can't drift silently between the two implementations again — an earlier attempt at this same fix had appended its note to a field the Excel export never actually reads, which would have made the flag invisible in practice despite being "implemented." **Verified PASS on a real machine (2026-09-30)**, full classification (239/239 supply, 900/900 demand) and full post-cap matching (2,586/2,586) both exact against fresh Python ground truth.

### Upload endpoint + Vaadin grids (2026-09-30, task #18)

The first real UI. Two ways to trigger a Supply/Demand refresh — a Vaadin upload page (two file-drop widgets, calls `RefreshService` in-process) and multipart REST endpoints for any non-browser consumer — both delegating to the same `RefreshService` built above. Two read-only grids (Supply, Demand) with the same filters (persona, sub-persona, location, classification status, active-only) the REST API already exposed; the filter logic itself was pulled out of the REST controllers into two shared query services so the grids and the API run identical code rather than two copies that could drift. A shared `AppLayout` shell ties Supply/Demand/Upload together as tabs. Deliberate gaps for this slice: no pagination (fine at 243/972 rows), minimal upload validation (a malformed file surfaces whatever exception the ingestion layer throws, not a friendly message), no auth on any of it.

### Shortlist workbook export (2026-09-30, task #19, then re-ported 2026-09-30)

A "Generate & Download" button (plus a matching REST endpoint) that runs a fresh matching pass at export time and produces the same "Phase 1 Shortlist" workbook the Excel Matching Engine section above describes — grouped by employee, tiered, with a live-recomputed "Read Me" methodology tab — rather than reading `match_candidates` (which only persists each signal's short quality code, not the full summary/detail text the workbook shows). Needed a small schema addition first: `Customer`/`Project Name`/`New-Ageing` (demand) and `Prime/NV` (supply) were pure display columns the workbook shows that had never been ingested at all, plus a same-shaped gap on the supply side to the classification-note fix already made for demand (Task above) — all added via `V6`.

**A real process failure, worth recording plainly rather than glossing over:** the first version of this export was ported from a stale, previously-packaged copy of `write_shortlist_workbook.py` (a deliverable folder, not the live working copy) without checking for a newer one — missing three columns ("MAS Mapping check", "Frontend Anchor check", "Additional Request (manual review only)") and a Sub-Capability suffix that the real, current Python tool already produces. The user caught this directly by comparing the generated workbook's columns against what they expected. Investigating it surfaced something important: **this was the exact same stale-reference-file mistake already made and fixed once before in this project**, for the matching engine itself (see the "AAFD-corrected... stale duplicate" note above, 2026-09-28) — the code that fixed it that time had already left a comment naming the true authoritative source, and that comment simply wasn't read before this export was built. On investigation, the good news was that the actual matching/classification engine needed no changes at all — it was already fully correct against the authoritative source — so the real fix was narrow: add the three columns and the header suffix to the export, all using data and helper functions that already existed from the classification-bug fixes above (nothing new needed in the schema or classification layer this time). Re-verified column-for-column against the authoritative Python source's column list and cell-styling rules.

**Still true for all of this, same as ever in this handoff:** none of this Java code has been independently compiled in the sandbox this project has mostly been built from (no Maven Central access there) — every "verified" claim above that doesn't explicitly say "on a real machine" should be read as "matches by inspection/logic trace, not yet run."
